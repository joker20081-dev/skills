# Zenn 技術記事の書き方

社内ドキュメントと公開技術記事の最大の違いは、**読者が前提を共有していない**ことと、**いつでも離脱できる**ことです。この 2 点がほぼ全ての判断の根拠になります。

## 構成の型

厳密なテンプレートではありませんが、多くの技術記事はこの骨格に収まります。

1. **冒頭（リード）** — この記事で何が分かるか、誰向けか。3〜5 行
2. **背景 / 課題** — なぜこれを調べたか。読者が「自分ごとだ」と思える具体的な状況
3. **結論** — 先に置く。長い記事ほど効く
4. **本編** — 手順、実装、検証、ハマりどころ
5. **まとめ** — 要点の再掲と、次に読むべきもの
6. **参考リンク** — `@[card]` でまとめる

`type: idea` の記事なら「課題 → 主張 → 根拠 → 反論への応答」のほうが自然です。

## 冒頭で離脱させない

読者は最初の数行で読むかどうかを決めます。

- **やること**: 「〜という問題に当たったので、〜で解決した記録です。同じ構成の人は 5 分で再現できます」のように、対象と得られるものを具体的に書く
- **避けること**: 「こんにちは、〇〇です。今回は〜について書いていきます」だけで本題に入らない前置き。自己紹介や挨拶が長い記事は読まれません

対象読者と前提（言語やライブラリのバージョン、OS）は冒頭に明記します。技術記事は古くなるので、**検証環境のバージョンを書くだけで記事の寿命が延びます。**

## コードの見せ方

- **動くコードを載せる**。断片だけ載せて読者が動かせない記事は価値が半減します。全体像は GitHub リポジトリへのリンクで補う
- **ファイル名を必ず付ける**（``` の後に `:src/app/page.tsx`）。どこに書くコードか分からないのが読者の一番のつまずきです
- **長いコードは折りたたむ**（`:::details`）か、要点だけ抜き出して差分表示（`diff`）にする
- コードの前に「何をするコードか」を 1 行、後に「なぜそう書くか」を書く。コードだけが並ぶ記事は読み飛ばされます

## 文章のトーン

- 「です・ます」で統一。技術記事で「だ・である」は硬すぎることが多い
- 一文を短く。「〜ですが、〜なので、〜という理由から〜」と続く文は分割する
- 断定できることは断定する。「〜かもしれません」「〜だと思います」が多いと、検証していない印象を与えます。**実際に検証していないなら、そう明記する**ほうが誠実です
- 過度な絵文字や過剰な装飾は避ける。emoji は frontmatter のアイキャッチで十分

## タイトル

検索とタイムラインの両方で戦うので、**具体的な技術名と、読者が得るもの**を入れます。

- ❌ `Next.js を触ってみた`
- ❌ `【完全保存版】Next.js のすべて`（誇張は敬遠されます）
- ⭕ `Next.js の Server Components でキャッシュに 3 回ハマった話と対処法`
- ⭕ `zod で API レスポンスを型安全にバリデーションする`

## よくある弱点

書き上がったら、この観点で自分の記事を読み返してください。

- **前提の飛躍** — 著者には自明な用語や手順が説明なしで出てくる。読者テストで最も多く見つかる問題です
- **試行錯誤の垂れ流し** — 「まずこれを試したがダメで、次にこれも試したがダメで…」が延々続く。失敗も価値がありますが、結論を先に置いて失敗談は後半か折りたたみに
- **出典なしの断定** — 仕様の話は公式ドキュメントへリンクする
- **スクリーンショットの多用** — コードやログはテキストで載せる。画像はコピーも検索もできません
- **バージョン非記載** — 半年後に「動かない」と言われる原因
